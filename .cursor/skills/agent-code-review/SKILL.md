# AI Agent 项目代码审查规范

## 审查流程

1. 先通读项目架构文档（ARCHITECTURE.md / README.md），建立全局认知
2. 按以下 10 大维度逐项检查，每条标注严重等级（P0 致命 / P1 严重 / P2 中等 / P3 建议）
3. 输出结构化审查报告：问题列表 + 严重等级 + 文件位置 + 修复建议
4. 最后给出总评分（10 分制）和优先修复 Top 5

---

## 维度一：Agent 架构基础（对应面试 Q1-Q2）

### 1.1 架构完整性
- [ ] 是否具备四大核心模块：LLM、任务规划、记忆、工具调用？缺哪个？`[P1]`
- [ ] Agent 与传统链式调用是否有明确区分？是否存在"伪 Agent"（硬编码线性流程但号称自主）？`[P1]`
- [ ] 各模块职责是否清晰？有无循环依赖或职责越界？`[P2]`

### 1.2 ReAct 模式实现
- [ ] think() → act() → observe 循环是否正确实现？`[P0]`
- [ ] 是否有最大迭代次数限制？无限制 = 潜在无限循环 `[P0]`
- [ ] observe 阶段是否正确处理工具返回的异常/空值/超时？`[P1]`
- [ ] 循环终止条件是否完备（任务完成、超出步数、超时、错误）？`[P1]`

---

## 维度二：多智能体协同（对应面试 Q3-Q4）

### 2.1 协作模式
- [ ] 多 Agent 协作模式是否明确（老板-员工 / 流水线 / 民主讨论）？`[P1]`
- [ ] 任务拆分粒度是否合理？过细导致通信开销爆炸，过粗导致子 Agent 理解偏差 `[P2]`
- [ ] 子 Agent 之间是否有不必要的耦合或直接通信？`[P2]`

### 2.2 防循环与防冗余
- [ ] 是否设置了全局最大迭代次数？`[P0]`
- [ ] Agent 间通信是否有摘要压缩机制？`[P2]`
- [ ] 是否有明确的任务完成标准和终止机制？`[P1]`
- [ ] 子 Agent 执行失败时的降级策略是什么？是否有重试/跳过/快速失败等多种策略？`[P1]`

---

## 维度三：记忆系统（对应面试 Q5, Q9）

### 3.1 短期记忆
- [ ] 是否使用上下文窗口管理当前对话？`[P1]`
- [ ] 上下文溢出时的处理策略：简单截断 vs 智能摘要？`[P1]`
- [ ] 对话摘要压缩是否会丢失关键信息？`[P2]`

### 3.2 长期记忆
- [ ] 长期记忆是否基于 RAG/向量存储？`[P1]`
- [ ] 记忆的写入时机是否合理（实时 vs 异步后处理）？`[P2]`
- [ ] 是否有记忆过期/清理机制？无限膨胀是隐患 `[P2]`
- [ ] 多用户场景下记忆是否有隔离（userId 过滤）？`[P0]`

### 3.3 状态管理
- [ ] 状态结构是否规范化（固定模板 vs 随意 Map）？`[P2]`
- [ ] 是否有上下文优先级：系统提示词 > 最近对话 > 核心任务目标？`[P2]`
- [ ] 历史对话压缩后是否保留了核心语境？`[P2]`

---

## 维度四：工具调用可靠性（对应面试 Q10）

### 4.1 调用安全
- [ ] 高危工具（文件操作、终端、转账等）是否有人工确认机制？`[P0]`
- [ ] 工具参数是否有强类型校验（JSON Schema / 强类型 DTO）？`[P1]`
- [ ] 是否有路径穿越（path traversal）防护？`[P0]`

### 4.2 异常处理
- [ ] 工具调用超时是否有重试机制？`[P1]`
- [ ] 工具返回错误信息是否会反馈给 LLM 让其自主修正？`[P2]`
- [ ] 是否有工具调用结果的分级处理（正常/空/垃圾/超时）？`[P2]`

### 4.3 循环检测
- [ ] 是否检测 Agent 反复调用相同工具且参数雷同的死循环？`[P1]`
- [ ] 检测到循环后是否有引导性干预（注入纠错提示）而非简单终止？`[P2]`

---

## 维度五：工作流引擎（对应面试 Q11）

### 5.1 灵活性
- [ ] 节点跳转是硬编码还是条件动态路由？`[P1]`
- [ ] 是否支持循环执行（Agent 试错迭代的核心能力）？`[P1]`
- [ ] 条件边的判断是否由 LLM 推理结果驱动？`[P2]`

### 5.2 安全性
- [ ] 工作流是否有死循环保护（最大步数 / 节点访问次数上限）？`[P0]`
- [ ] 人工审批节点是否支持超时处理？`[P2]`
- [ ] 工作流执行状态是否可持久化和恢复？`[P2]`
- [ ] 条件表达式是否安全（避免任意代码执行 / 脚本注入）？`[P0]`

---

## 维度六：质量评估体系（对应面试 Q12）

### 6.1 评估指标
- [ ] 是否有任务成功率追踪？`[P1]`
- [ ] 是否追踪平均推理步数（越少越好）？`[P2]`
- [ ] 是否有工具调用准确率统计？`[P2]`
- [ ] 是否支持影子测试（新旧逻辑对比）？`[P3]`

### 6.2 自检机制
- [ ] Agent 输出是否有质量审查（红蓝对抗 / 自审 / 交叉审核）？`[P1]`
- [ ] 审查模型是否与主模型独立（避免自我审查偏见）？`[P2]`
- [ ] 高风险场景是否强制质量审查？`[P1]`
- [ ] 是否有 Reflexion 机制记录失败轨迹避免反复踩坑？`[P3]`

---

## 维度七：RAG 系统（对应面试 Q13-Q16）

### 7.1 检索质量
- [ ] 是否采用混合检索（向量 + BM25 关键词）？`[P2]`
- [ ] 是否有重排序（rerank）模型精排？`[P2]`
- [ ] 文档切块是否语义感知（按标题/段落 vs 固定长度）？`[P2]`
- [ ] 是否支持多查询扩展（同一问题多种问法并行检索）？`[P3]`

### 7.2 冲突与权限
- [ ] 检索内容冲突时的取舍策略（时间权重 / 权威度排序）？`[P2]`
- [ ] 是否有权限隔离（向量数据绑定访问控制）？`[P0]`
- [ ] 是否要求输出附带检索来源（强制溯源）？`[P2]`

### 7.3 动态适配
- [ ] 实时更新的知识库是否有增量更新机制？`[P3]`
- [ ] 是否有缓存失效策略？`[P3]`
- [ ] 检索结果不足时是否会自动重新检索或拒绝回答？`[P2]`

---

## 维度八：安全防护（补充维度）

### 8.1 Prompt 注入防护
- [ ] 用户输入是否有注入检测（Prompt Injection）？`[P0]`
- [ ] 系统提示词是否有防泄漏措施？`[P0]`

### 8.2 访问控制
- [ ] Agent 调用外部服务是否有权限校验？`[P0]`
- [ ] MCP 服务是否有信任等级机制？`[P1]`
- [ ] 是否有"一票否决"式的访问决策层？`[P2]`

### 8.3 执行隔离
- [ ] 终端/文件等危险工具是否在沙箱中执行？`[P0]`
- [ ] 沙箱策略是否可配置（无沙箱 / 进程沙箱 / Docker 沙箱）？`[P1]`

---

## 维度九：工程质量（补充维度）

### 9.1 构造器与依赖注入
- [ ] 是否存在超大构造器（>10 个参数）？考虑 Builder 模式或聚合参数 `[P2]`
- [ ] 依赖注入是否规范？是否有手动 new 对象导致测试困难？`[P2]`

### 9.2 可观测性
- [ ] 是否有执行轨迹记录（Trace）支持？`[P1]`
- [ ] 关键决策点是否有日志？`[P2]`
- [ ] 是否有用量统计和成本追踪？`[P2]`

### 9.3 测试覆盖
- [ ] 核心 Agent 逻辑是否有单元测试？`[P1]`
- [ ] 多 Agent 编排路径是否有集成测试？`[P1]`
- [ ] 工具调用是否有 mock 测试？`[P2]`
- [ ] 记忆系统是否有持久化兼容性测试？`[P2]`

### 9.4 配置管理
- [ ] 敏感配置（API Key 等）是否外部化？是否硬编码？`[P0]`
- [ ] 生产环境配置是否完整？空 prod profile 是隐患 `[P1]`

### 9.5 持久化
- [ ] 文件持久化是否考虑了并发安全（读写锁）？`[P1]`
- [ ] 文件持久化是否考虑了生产环境可伸缩性？`[P2]`
- [ ] JSON 序列化是否有版本兼容和迁移机制？`[P3]`

---

## 维度十：生产就绪度（补充维度）

### 10.1 容错
- [ ] LLM 调用失败是否有降级策略（换模型 / 返回兜底）？`[P1]`
- [ ] 向量数据库连接失败是否影响核心流程？`[P1]`
- [ ] 异步任务是否有超时兜底？`[P1]`

### 10.2 性能
- [ ] 记忆查询是否并行（而非串行逐层查询）？`[P2]`
- [ ] 是否有合理的 Token 预算控制？`[P1]`
- [ ] SSE 流式响应是否处理了连接断开？`[P2]`

### 10.3 部署
- [ ] Dockerfile 是否使用多阶段构建减小镜像体积？`[P3]`
- [ ] 是否有健康检查端点？`[P2]`
- [ ] 是否有压力测试脚本？测试覆盖哪些场景？`[P3]`

## 评分标准

- **9-10**：生产级，所有 P0 清零，P1 ≤ 2
- **7-8**：良好，P0 ≤ 1，P1 ≤ 5
- **5-6**：基本可用，P0 ≤ 3，P1 ≤ 10
- **3-4**：问题较多，P0 > 3 或有致命架构缺陷
- **1-2**：原型阶段，大量核心功能缺失
